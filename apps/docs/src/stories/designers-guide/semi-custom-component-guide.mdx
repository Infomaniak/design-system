# Creating a semi-custom component

A semi-custom component is a custom container that assembles native components from the kit. Use
this guide only when no native component covers the need, even with its properties or slots.

> 👑 **Golden rule:** native parts stay native. They remain linked instances of the official kit,
> never detached or overridden, so that a kit update reaches the component without anyone touching
> it.

The container uses the tokens of its kit. Native instances keep their own.

## 1. Design in context 🎨

- Start with a simple frame in auto layout and drop in real instances from the kit. Don't redraw
  elements that look native.
- Place it in a real screen filled with real content. At this stage, it's not a component yet.
- Once the concept is set, validate it with the DS team and the dev teams. Each native part must
  have a code equivalent.
- Once it's validated, convert it into a component, add the container's states and/or variants,
  then move on to step 2.

## 2. Name your component 🏷️

- Use **kebab-case** for the component name (e.g. `calendar-event`, `event-card`).
- For an iOS/iPadOS 🍎 or Android 🤖 component, follow the **native naming** of the platform kit
  instead, so the component reads like the native ones next to it.
- Native instances inside the component keep their native name (Button, Toggle…).
- For an internal subcomponent that must not be published, prefix its name with `.` or `_`: Figma
  won't publish it to the library.
  - Use the same prefix as the native kit the component belongs to.
  - If there's no native convention to follow, use `.` (e.g. `.month-cell`).

## 3. Expose, don't duplicate 🔗

- Expose the properties of nested native instances instead of recreating them on the container.
- Don't recreate native states as variants of the container: a disabled Button is handled by the
  Button itself.

  src={SemiCustomComponentExposeDontDuplicate}
  alt="A snackbar component exposing its nested native Button instance vs one recreating the Button states as variants"
/>

## 4. Test the edge cases 😥

- Very long text
- Empty content
- Variable widths
- Native states inside each container state
- Liquid Glass background for iOS/iPadOS 🍎

## 5. Ready-to-use component checklist ✅

### Native instances

- Native parts are linked instances from the official kit library
- No detached instances, no overrides beyond their own properties
- Native layers keep their native name (Button, Toggle…)

### Tokens

- The container uses the tokens of its kit, with no hard-coded values
- Text styles are applied, not local sizes and weights
- The component is checked in light and dark mode
- Icons come from Iconography, with no imported or flattened icons

### Properties

- Default values are usable as is (default state, realistic text)
- Properties are properly named, in English, using native kit naming whenever possible
- Showing or hiding an element uses a boolean, not a variant
- Instance swaps and slots only offer the allowed native components
- No unused or invalid properties left behind

### Structure

- Auto layout is applied
- Layers are named, with no hidden layers or leftover groups
- The component resizes correctly (hug and fill tested)
- Long-text behavior is defined (wrapping or truncation)
- The component is named in kebab-case, or follows the native kit naming (see step 2)
- Internal subcomponents are prefixed with `.` or `_`, following the native kit convention (`.` by
  default)

## 6. Integration into the kit by the DS team 🌼

- All states required by the kit are present
- A usage doc explains why this component exists instead of a native one, and lists the native
  components it relies on
